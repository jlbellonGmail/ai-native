## Design decision for the human (deviation from the approved 002 plan)

The 002 plan designed a new `acceptance-governance.yml` holding the `ai-native-trust` App key. Per the instruction
to minimize key holders, the candidate instead runs the analysis in a secret-free job of the existing
`merge-gate.yml` and publishes through its existing holders (exactly two holder workflows, enforced by
`secret-exposure.test.mjs`). Consequence: the trusted verdict exists only for PRs to `main` (where merge-gate runs);
for `develop` RF-25 is BLOCKED until the human decides to run the gate there as well. The plan text
(`specs/002-native-acceptance/plan.md`) is unchanged and needs the human's acceptance of this deviation.

Two further deviations from the 002 text need the same explicit acceptance (fifth review R5-2, R5-3). They are
not spec amendments, and a spec amendment for v4.1.x is the follow-up:

* **RF-30 at merge (audit S-58).** The trusted verdict selects features by case inputs and does not re-apply the
  uncovered-path BLOCK; only the local circuit view does (`verdict.test.mjs` asserts PASS for a change outside every
  input). Applying it at merge would BLOCK every release PR with no human path, because the release procedure
  commits `.audit/reports/*.md` and RF-34 cannot admit `.audit/`.
* **RF-31 human override (audit N-58).** A closure produced by a changed producer (`ci.yml`, `ci-closure.mjs` and
  its imports) is not rejected outright. It becomes `CLOSURE_PRODUCER_CHANGED`, which only the human Environment
  approval clears; FAIL and BLOCKED still dominate. The approval is only as independent as U0 (and, in consumers,
  as their mandatory review of `.github/**`).

## First activation of the trusted path (after the human merge of v4.1.0 to `main`)

**What judges the initial promotion (v4.0.2 controls, the BASE copy on `main`).**

* Ruleset `ai-native-main` (24405506): no bypass actors, deletion and non-fast-forward blocked, PR required, strict
  required checks:
  * `validators (ubuntu-latest)`, `validators (windows-latest)`, `pin-check` and `pr-gate`, from GitHub Actions;
  * `ai-native/trust-gate` and `ai-native/merge-gate`, from App 5170488.
* The v4.0.2 `trust-gate.yml` and `merge-gate.yml` run from BASE (`pull_request_target`). A control-plane change
  is neutral, so `human-review` waits for the `ai-native-human-review` approval (`can_admins_bypass: false`).
* The release procedure: PLATFORM audit of the exact head under `.audit/**`, then `release-gate` and `pretag`.
* The v4.1.0 acceptance verdict does NOT judge this PR.

**What starts to govern afterwards.**

* The v4.1.0 `merge-gate.yml` (job `acceptance-analyze` plus the existing holders) runs for every PR event to
  `main` from the merge commit on.
* Its verdict is folded into the check that is ALREADY required, `ai-native/merge-gate`. With no verdict,
  `ACCEPTANCE_BLOCKED` makes that check fail: a missing or invalid verdict file through `evaluateAcceptance`
  (`runtime/gates/merge-gate.mjs:60`), folded into the decision at `:96-98`.
* No ruleset change is needed, so there is no window in which the required check is absent.

**Why there is no unprotected interval.**

* `main` changes only through PRs (no bypass actors).
* `pull_request_target` uses the workflow of the base at event time.
* With `strict_required_status_checks_policy`, a PR opened earlier (e.g. Dependabot) must be updated to the new
  `main`. The new head SHA has no checks until the new merge-gate publishes them.

**How the first real run is verified (human, right after the merge).**

1. Open a canary PR to `main` from a branch off `main`, changing only `governance/execution/current/`. It is
   non-SUT, selects no feature and has a CI run with `acceptance-closure`.
   * Expected: `acceptance-analyze` succeeds and the `acceptance-verdict` artifact has `status: PASS` and
     `headSha` = the PR head.
   * Check runs `ai-native/acceptance-governance` and `ai-native/merge-gate` come from App 5170488 on that SHA.
2. Push to the same PR a comment-only change to `runtime/main.mjs`. It is a case input of 001-003 and not part of
   the closure producer (`producerSurface`: 23 files, `runtime/main.mjs` not among them).
   * Expected: the verdict is `NEEDS_HUMAN` (`CLOSURE_NOT_ISOLATED` ×3, and no `CLOSURE_PRODUCER_CHANGED`
     because the producer is unchanged).
   * `ai-native/acceptance-governance` stays pending until the `ai-native-human-review` approval, then becomes
     `ACCEPTANCE_APPROVED by <humanMerger>`.
3. Close the canary without merging, or merge the first commit only, at the human's choice.
4. Verify with:
   * `gh run view <merge-gate run> --log`;
   * `gh api repos/jlbellonGmail/ai-native/commits/<sha>/check-runs` (app id 5170488);
   * the downloaded `verdict.json`.

**Rehearsal already done, read-only (not evidence from `main`).**

* The `acceptance-analyze` steps were replayed with the v4.1.0 code against the real PR #190 (head `a97cc98`, CI
  run 46020803733, job 140579781011, base `develop`). The same `gh api`/`jq` queries found the run, downloaded
  the artifact and the job log (3 anchors).
* `verdict.mjs` gave `NEEDS_HUMAN`: `CLOSURE_NOT_ISOLATED` ×3, `CLOSURE_PRODUCER_CHANGED` ×18 (#190 creates the
  producer), `CONTRACT_CREATED`, `CUTOFF_CREATED`. 001, 002 and 003 are PASS in `restricted`.
* It matches audit probe V-63. The App token and Environment steps cannot be rehearsed outside `main`.

**What stops the continuation (no further PR to `main` until resolved).**

* `acceptance-analyze` or `merge-gate-job` fail or are skipped.
* No `ai-native/acceptance-governance` check.
* A verdict with a `headSha` other than the PR head.
* Any unexpected `BLOCKED`.
* Above all, `PASS` where step 2 expects `NEEDS_HUMAN` (a fail-open).

**Recovery without weakening protections.**

* A transient failure (API 5xx, runner loss): re-run the failed jobs (`gh run rerun <id> --failed`). The verdict is
  recomputed for the same SHA.
* A deterministic defect that yields `NEEDS_HUMAN`: a forward-fix PR, approved through the Environment. It keeps
  specs 001-003, the contract, the plans and the `acceptance-closure` job.
* Not a full revert, nor GitHub's "Revert" button: once v4.1.0 is on `main`, that PR is judged by the v4.1.0 gate
  and is BLOCKED with no human path. It deletes REQUIRED features (`verdict.mjs` deriveClosure) and the closure
  job (fifth review R5-1, R5-7).
* A defect that BLOCKS every PR (including a forward fix), or the need for a full revert, has no path inside the
  protections: the ruleset has no
  bypass actor and the Environment has no admin bypass. Any exit (a temporary ruleset change) is a human decision
  outside this candidate and would weaken the protection. The rehearsal above and the canary exist to detect this
  BEFORE any other change waits on `main`.
* A fail-open (step 2 PASS): stop all merges to `main` and fix forward with a PR that restores the expected
  verdict. That PR changes the control plane, so it still needs the `ai-native-human-review` approval (trust-gate
  neutral). The canary must not be merged.
* Unverified risk (fifth review): the jobs check out `pull_request.base.sha`. If an event carried a pre-v4.1.0
  base SHA, the v4.0.2 `merge-gate.mjs` (which ignores the verdict) would run under the new workflow. The canary
  log shows the checked-out BASE. Strict required checks make a stale head unmergeable. Update every PR opened
  before the merge, and confirm its merge-gate run checked out the current `main`.
