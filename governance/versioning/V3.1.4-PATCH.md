# v3.1.4 — parche de plataforma: `ai-native init`

Estado: **CANDIDATA** (sin tag, sin release). `v3.1.3` es inmutable y no se modifica ni se mueve. La publicación es posterior al merge humano de la PR y sigue el proceso vigente (`release.yml` sobre el tag).

## Causa raíz

Convertir un repositorio vacío en consumidor exigía conocer detalles internos: `node runtime/bootstrap/cli.mjs init --bundle <tar.gz> --repo github:… --profile …`, descargar el bundle con `gh release download`, verificar con `gh attestation verify`, `sync`, `run -- adapters`, `status`. Esas primitivas existen, están probadas y son correctas, pero (a) **no había una fachada**: ningún camino público las componía, y (b) había un **problema de huevo y gallina**: el lanzador `.ai-native/ai-native.mjs` y el bootstrap viven *dentro* de la release, así que un repositorio vacío no tenía por dónde empezar. No faltaba una capacidad de verificación; faltaban la orquestación y un punto de entrada que se pueda obtener sin tener ya la plataforma.

## UX antes y después

| | Antes | Después |
|---|---|---|
| Repo vacío → consumidor | 6+ comandos internos, rutas del runtime, bundle, `--repo`, `--profile`, hash en el lock | `ai-native init` |
| Perfil | `--profile python-service` obligatorio | detectado del repositorio; si no hay señal, una pregunta; sin TTY, error con el comando exacto |
| Resultado | exit code de cada primitiva | `STATUS: READY` / `AI-NATIVE:` / `DRIFT: CLEAN` / `ATTESTATION: PASS` / `REVOCATION:` |
| Segunda ejecución | `init` fallaba («lock already exists») | reverifica sin tocar un byte (`ALREADY_ADOPTED`) |

Comando público definitivo: **`ai-native init`** (semántica del `init` ya existente; `adopt` quedó como nombre interno del motor porque el comando no «adopta» solo: también reverifica). Opciones avanzadas: `--profile`, `--version`, `--offline`, `--keep-existing`, `--json`. Una vez por máquina: `ai-native install` (README, «New project»).

## Arquitectura (reutiliza lo existente; no introduce npm, binarios ni `curl | sh`)

```text
ai-native-cli.mjs   (asset de release, atestado; runtime/cli/ai-native.mjs; sin dependencias; es lo ÚNICO que corre antes de verificar)
  1. repo Git (toplevel) ; lock existente => la release la decide el lock; si no, --version o la última ESTABLE, PUBLICADA e INMUTABLE (API de releases)
  2. caché con registro de attestation verificada => sin red ; si no, descarga + sha256 contra el digest que GitHub publicó
  3. `gh attestation verify --repo … --signer-workflow <repo>/.github/workflows/release.yml` OBLIGATORIO (sin flag para saltarlo)
  4. desempaqueta (lector tar estricto) en un temporal privado y cede el control al motor DEL BUNDLE VERIFICADO:
       runtime/bootstrap/cli.mjs adopt  ->  runtime/bootstrap/adopt.mjs
         revocations (fail closed) -> perfil (profile-infer.mjs) -> caché (put/verify) -> init (lock) -> sync
         -> adapters (applyConsumer, brownfield-safe) -> git add de lo gestionado -> verify (status, drift, tracking, doctor)
         -> fallo en cualquier punto: rollback de lo escrito (lock, proyecciones, journal)
```

* **Chicken-and-egg:** el asset `ai-native-cli.mjs` es el punto de entrada portable. Se obtiene con `gh release download` y se verifica con `gh attestation verify` (README) y se instala con `node ai-native-cli.mjs install` (copia a `~/.ai-native/bin` y shims `ai-native` / `ai-native.cmd`; no edita el PATH, dice qué línea añadir). No depende de ninguna ruta de la máquina del maintainer.
* **Por qué no npm / `npx github:` / binario:** exigen un registro o una cadena de confianza nueva (el tag no está protegido, F-04) o una toolchain de compilación para tres plataformas. `gh` ya es el verificador de la plataforma (`verify-release`, `bootstrap sync --require-attestation`).
* **Perfil:** `pyproject`/`requirements*`/`supabase/`/`mkdocs.yml` + marcadores de servicio (`fastapi`, `Dockerfile`, `openapi.yaml`…). Repo vacío o solo README: **no hay señal y no se adivina**; se pregunta (TTY) o se falla cerrado listando las opciones. Para `gi-common-reference` (misma familia que `gi-common-persons`, `python-service` en M6): `ai-native init --profile python-service`, o elegir «python-service» en la pregunta.
* **Qué escribe:** `ai-native.lock.json`, `CLAUDE.md`, `.mcp.json`, `.codex/*`, `opencode.json`, `.claude/**`, `.opencode/**`, `.ai-native/ai-native.mjs`, `.ai-native/adoption-journal.json`; y los **deja en el índice** (sin eso `tracking` los juzgaría no reproducibles en un clon limpio). No commitea. `AGENTS.md` es del proyecto: si falta, avisa.

## Garantías conservadas (ninguna rebajada)

| Garantía | Cómo |
|---|---|
| release pinning | el lock lo crea `init()` con el digest del bundle verificado; con lock, la release la decide el lock |
| digest | sha256 del asset contra el digest publicado por GitHub (`DIGEST_MISMATCH`) y contra el lock (`sync`) |
| attestation / provenance | `gh attestation verify` con `--signer-workflow` del workflow de release, sobre el archivo exacto; el motor exige el registro y que su `digest` sea el del bundle |
| fail closed | sin `gh`, attestation fallida, bundle corrupto, digest distinto, release revocada o lista de revocaciones ilegible (`REVOCATION_UNKNOWN`, salvo `--offline` declarado): nada se escribe |
| inmutabilidad | solo releases con `immutable !== false`, no draft, no prerelease; `v3.1.3` y anteriores no se tocan |
| caché segura / offline | la caché es direccionada por contenido y se reverifica en cada lectura; el registro `attestations/<hex>.json` se escribe solo tras verificar; `--offline` exige release + registro y no usa red; caché manipulada: la release se cura desde el blob verificado, el blob manipulado falla cerrado |
| ejecución de contenido remoto | nunca se ejecuta código descargado antes de verificarlo; el único código previo a la verificación es el propio asset atestado |
| trust gate / drift / plano de control | sin cambios; `release.yml` (plano de control) solo añade el asset |

## Límites honestos

* **Confianza en la primera instalación:** el asset se verifica con `gh attestation verify` *antes* de ejecutarlo (README), pero quien ejecuta `gh` confía en `gh` y en la raíz de confianza de Sigstore/GitHub, como con cualquier CLI. No hay equivalente sin `gh`: sin `gh` el comando falla cerrado (no existe verificación sigstore en Node sin dependencias).
* **`release.yml` no se ejercita completo hasta publicar:** en PR corre solo `build` (dry run, ahora con el asset); `publish` y `verify` (incluido el acceptance test desde el asset publicado) corren con el tag. Si fallaran, la release no se verifica y se trata como incidente de release (no se edita: se publica el siguiente parche).
* **El primer `ai-native init` real contra GitHub solo es posible tras publicar `v3.1.4`** (el motor vive dentro de la release). Hasta entonces la prueba extremo a extremo usa un bundle construido del árbol y la red simulada.
* **Consumidores adoptados** (los 9, en `v3.1.2`): no se tocan. `ai-native init` sobre uno de ellos descarga su release fijada, verifica y falla cerrado con «predates `ai-native init`» (esa release no trae el motor) hasta que se suba el lock; no escribe nada.
* El registro de attestation en la caché es local y del usuario: quien controle `AI_NATIVE_CACHE` controla lo que corre (mismo modelo que el lanzador L3).
* Windows: `git add` reintenta ante «Permission denied» transitorio (antivirus/indexadores).
