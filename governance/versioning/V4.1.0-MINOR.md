## Version: v4.1.0 (MINOR)

By `VERSIONING-POLICY.md`: new capability, new schemas and optional schema fields, a new reusable-workflow input
(`acceptance-environment`, `acceptance-reviewers`, optional). Not MAJOR: the consumer lock, the bootstrap contract
and the core skills are unchanged, and no schema or reusable-workflow input is removed or changed incompatibly;
the factory `AGENTS.md` control-plane list grows (factory only, not the consumer template).

**Policy tension for the human:** MINOR says new gates start in *warn* mode for one MINOR. Specs 002/003 (approved)
make acceptance blocking at closure for *new* features; existing features are protected by the legacy cutoff the
upgrade writes (they keep v4.0.2 behavior), and `sdd validate --level normal` keeps the v4.0.2 warning. The human
decides whether that satisfies the policy or requires a warn-mode period.

## Consumer delta

Upgrade from exactly v4.0.1, v4.0.2, v3.4.2, v3.4.3 (v3.4.x reports the MAJOR crossing); the legacy cutoff is

versions dropped both silently. Locks without those fields serialize byte-identically.

## Promotion steps (human; the agent performs none of them)

Order of merges (each one is a human merge with a merge commit):

1. **PR #190** (`feature/native-acceptance-v4.1.0` -> `develop`). It is the human decision on the content, the
   key-holder deviation and the bootstrap (`V4.1.0-STATE.md`, "Human decisions").
2. **Release PR** (`release/v4.1.0-r3` -> `main`).
   * Its head must be the audited SHA plus only the `.audit/**` report commit. `main` is already an ancestor
     (strict checks).
   * If `develop` received other changes that must ship, they go into a new branch `release/v4.1.0-r4` (from
     `release/v4.1.0-r3`, merging `develop`), and that head is re-audited. The release branch is not rebuilt from
     `develop` by reset.
   * The PR is judged by the v4.0.2 controls of `main` (`pull_request_target` runs the BASE `merge-gate.yml`),
     **without** the new acceptance verdict (bootstrap). Required checks:
     * `validators` ×2, `pin-check` and `pr-gate`;
     * `ai-native/trust-gate` and `ai-native/merge-gate` (App 5170488);
     * the `ai-native-human-review` approval for the control-plane change.
   * Also confirm green: `acceptance-closure`, `acceptance-pilot`, CodeQL and supply chain.
3. **Pretag, after the merge.** Run `git fetch origin main --tags`, then
   `node runtime/release/pretag.mjs --tag v4.1.0 --candidate <merge SHA> --repo jlbellonGmail/ai-native`, which must
   give READY. The merge commit's tree equals the audited tree plus `.audit/**`, so the report stays current.
4. **First activation of the trusted path**, before any other PR to `main`: the canary PR to `main` described in
   `V4.1.0-STATE.md`, "First activation". A stop condition there halts the promotion.
5. **Tag** `v4.1.0` (human), release workflow, post-release verification.
6. **Sync PR** `main` -> `develop`, so the CLI bump, this record and the audit report reach `develop`.

The human may swap steps 4 and 5. Tagging first publishes a release whose trusted path has not yet run from
`main`.
