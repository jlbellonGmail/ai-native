# v3.3.0 — versión menor de plataforma: lifecycle completo del CLI global

Estado: **CANDIDATA** (sin tag, sin release). `v3.2.0` es inmutable y no se toca. La publicación es posterior al merge humano de la PR
(`governance/security/HITL-MERGE-POLICY.md`) y sigue el proceso vigente (`release.yml` sobre el tag).

## Causa raíz

`v3.2.0` entregó el CLI global sin ciclo de vida: sin versión propia, sin forma de actualizarlo, sin contrato con la PLATFORM (contrato implícito sobre
nombres de assets, flags y argumentos del motor), sin revocación y con `install` no atómico. Esta release lo cierra.

## Modelo

| | CLI global | PLATFORM del repositorio |
|---|---|---|
| Versión | `CLI_VERSION` en `runtime/cli/ai-native.mjs` = tag de la release que lo publica (el build lo exige) | `platform.version` en el lock |
| Vive en | `~/.ai-native/bin` | caché por digest; referenciada por `ai-native.lock.json` |
| Se actualiza con | `ai-native self-update` | `ai-native upgrade` (explícito; nunca solo) |

`ai-native --version`: `CLI: vX.Y.Z` y, dentro de un repo adoptado, `CLI: vX.Y.Z | PLATFORM: vA.B.C`.

## Contrato CLI ↔ PLATFORM

`contracts/bootstrap-protocol.json` se publica en `platform.json` como `bootstrap` `{ protocol, minCliVersion, requiredCapabilities }`
(`platform.schema.json`; ausente en releases anteriores = protocolo 1, CLI >= v3.2.0, `[adopt]`). La negociación es doble y fail closed
(`INCOMPATIBLE_CLI`, con el remedio): la hace el CLI antes de ceder el control y la repite el **motor** del bundle (`runtime/bootstrap/compat.mjs`), que
es lo único que protege a los CLI ya instalados: un CLI v3.2.0 no envía `--cli-version`, y esa ausencia lo identifica como *legacy* (v3.2.0,
protocolo 1, `[adopt]`). v3.3.0 declara `minCliVersion: v3.2.0`: los CLI instalados siguen funcionando y solo avisan (`LEGACY_CLI`).

## Comandos nuevos

`upgrade [--to]`, `detach [--keep-modified]`, `self-update [--check]`, `uninstall [--purge-cache]`; `install` endurecido. El CLI sigue siendo pequeño:
descubrimiento, confianza, compatibilidad y autogestión. `upgrade` y `detach` viven en el motor firmado (`runtime/bootstrap/upgrade.mjs`, `detach.mjs`).

* **upgrade**: release objetivo (la última estable inmutable o `--to`) verificada como en `init` (sha256 publicado, attestation del workflow de release,
  revocaciones); sin downgrade; calcula commit y digest; mueve lock, el pin del workflow de *esta* repo y las proyecciones gestionadas como delta mínimo
  (lo editado se conserva y se avisa); sync; verifica status, drift y tracking; ante cualquier fallo restaura exactamente lo anterior (archivos e índice,
  comprobado contra `git status`). Nada se commitea.
* **detach**: solo lo que el journal dice que ai-native escribió y sigue idéntico; un gestionado editado => `DETACH_BLOCKED` nombrándolo y sin tocar nada
  (`--keep-modified` lo deja como archivo ordinario); lo que ya existía idéntico, `.github/workflows/ai-native.yml` y migraciones v2 no se tocan.
* **self-update**: mayor estable inmutable; sha256 publicado; `gh attestation verify --signer-workflow`; revocación `kind: cli`; el asset debe declarar el
  tag; sin downgrade; preparado en `bin/`, arrancado con `version --json` antes de confiar, reemplazo por rename (reintenta bloqueos de Windows), `.prev`
  conservado, segunda sonda y vuelta atrás si falla. Sin red o sin `gh` no cambia nada.
* **install**: idempotente; nunca instala un CLI más viejo sobre uno más nuevo; mismo staging, rename y sonda; la pista de PATH de Windows opera solo sobre
  el PATH de *usuario* y sin duplicar (antes copiaba el PATH de proceso, que incluye el de máquina, al de usuario).
* **uninstall**: programa, shims y restos de staging; no toca PATH ni repos, y la caché solo con `--purge-cache` y si es reconociblemente una caché.

## Seguridad

Revocación del CLI en su propia serie `cli-revocations-<n>.json` (misma raíz de confianza, atestada por el mismo workflow; el build, `release.yml` y
`verify-release` la exigen). Va separada de `revocations-<n>.json` a propósito: un motor anterior falla cerrado ante una lista que no entiende, y una
entrada `kind: cli` ahí habría roto todas las releases viejas. Recuperación externa ante un CLI comprometido: `governance/security/CLI-RECOVERY.md`.
Ninguna garantía de v3.2.0 se rebaja.

## Transición desde v3.2.0 (única excepción histórica)

El código v3.2.0 no puede conocer `self-update`. Una sola vez, a mano: descargar `ai-native-cli.mjs` de la release, `gh attestation verify` y
`node ai-native-cli.mjs install` (reemplaza el v3.2.0). Desde entonces el ciclo es autosostenible. Los repos adoptados con v3.2.0 no cambian.

## SemVer

Capacidades públicas nuevas y aditivas, campos opcionales en contratos y compatibilidad con los CLI instalados: **MINOR, `v3.3.0`**.

## Pruebas

`runtime/cli/ai-native-lifecycle.test.mjs`: versión; init respeta el lock; upgrade (lock, pin, proyecciones, SemVer `v9.10.0 > v9.9.3`, ediciones
locales, rollback verificado, sin downgrade, offline, sin journal, revocada, digest, attestation); matriz de compatibilidad con el CLI **v3.2.0 real**
(`evaluation/fixtures/cli/`, byte a byte, mínimo soportado) y con releases que exigen más; self-update (check, atómico, digest, attestation, signer, `gh`
ausente, versión declarada, asset roto, offline, revocado, sin downgrade, fallo al reemplazar, reemplazo con Node cargado); install y uninstall
(idempotentes, rutas con espacios, PATH); detach; multi-repo (v9.9.1/2/3 con un CLI) y multi-equipo (clon con caché vacía). `release.test.mjs` y
`verify-release` cubren el asset de revocaciones del CLI y que el CLI declare el tag; `verify-release` ejecuta el CLI v3.2.0 contra la release publicada.
Windows y Linux: la matriz `validators (ubuntu-latest | windows-latest)` los ejecuta.

## Límites honestos

* Un CLI v3.2.0 no puede actualizarse solo ni conocer `cli-revocations`: es la excepción de transición.
* La compatibilidad hacia atrás se prueba contra el CLI v3.2.0 como mínimo; cada subida de `minCliVersion` debe añadir su fixture.
* `self-update` protege contra un asset malo, no contra un CLI instalado ya comprometido (ver `CLI-RECOVERY.md`).
